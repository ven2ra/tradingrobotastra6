# MOEX Multi-strategy terminal

React/TypeScript/Tailwind терминал с восемью экранами, реальными котировками T-Invest и отдельным paper-движком. Монитор получает данные; торговые решения и отправка paper-заявок принадлежат backend. [Архитектура и стратегии](docs/design.md).

## Интерфейс

```powershell
cd frontend
npm ci
npm run dev
```

Открыть http://127.0.0.1:5186. Реальные котировки T-Invest (Watchlist, Режимы рынка, Журнал, Облигации) работают всегда, независимо от выбранного режима исполнения. Переключатель «Paper / Live» в шапке выбирает, чей портфель показывают «Обзор» и «Портфель»: по умолчанию Paper (виртуальный движок backend), «Live» — ваш реальный брокерский счёт по личному токену (замочек на кнопке исчезает после того, как счёт подключён). UI никогда не подставляет демо-данные при ошибке реального API.

Конструктор всех восьми классов и риск-политика проверяют JSON Schema, сохраняют локальные черновики и экспортируют JSON. Черновики **не активируют** стратегию. Журнал имеет поиск, фильтры и экспорт; Watchlist сохраняется в браузере. Live показывает предупреждение и блокировку запуска.

## T-Invest

Скопировать `.env.example` в `.env`, указать `T_INVEST_TOKEN` только на сервере. Для котировок достаточно токена с доступом на чтение; браузер токен не получает. `.env` исключён из Git и Docker build context. При компрометации токен необходимо отозвать у брокера.

`T_INVEST_INSTRUMENTS` задаёт `TICKER_BOARD` через запятую; пустое значение включает поиск до `T_INVEST_MAX_INSTRUMENTS` ликвидных инструментов (максимум 300). Полный проход по большому списку дольше интервала опроса: лимит запросов ограничен, одновременно обрабатывается не более трёх инструментов. UI показывает время каждой цены; устаревшая котировка или стакан переводят режим в UNDEFINED. `T_INVEST_POLL_SECONDS` — пауза между завершёнными проходами полного каталога (не гарантия обновления всех 300 бумаг каждые 15 секунд), а не частота обновления Watchlist.

Тикеры из Watchlist браузера обновляются двумя быстрыми фоновыми циклами, отдельными от медленного прохода по всем 300 инструментам. Фронтенд передаёт текущий Watchlist backend'у на каждом опросе (`GET /api/t-invest/snapshot?priority=SBER,GAZP,...`), а `Observer.set_priority()` сопоставляет тикеры с каталогом:

- `T_INVEST_PRIORITY_POLL_SECONDS` (по умолчанию 2 сек) — один пакетный `GetLastPrices` на весь список сразу, независимо от числа бумаг; обновляет только цену и её время.
- `T_INVEST_PRIORITY_SIGNAL_POLL_SECONDS` (по умолчанию 8 сек) — полный анализ (стакан, статус торгов, свечи, сигналы плагинов Grid/Trend/MeanReversion — тот же `instrument()`, что и в медленном проходе) именно для бумаг из Watchlist, не дожидаясь их очереди среди 300 инструментов. Именно эти сигналы создают Live-предложения на подтверждение.

Оба цикла делят с медленным проходом общий rate-limit клиента, поэтому не могут превысить лимит запросов брокера — они просто перераспределяют его в пользу того, что реально смотрит пользователь. Бумаги вне Watchlist по-прежнему обновляются только медленным полным проходом.

Каталог T-Invest автоматически пополняется ликвидными инструментами: ориентир — 100 акций и 200 облигаций, с заполнением свободных мест другим классом, если одного недостаточно. Отбор: RUB, основные доски MOEX, `liquidityFlag=true`, доступ через API. Это признак ликвидности брокера, не рейтинг по текущему обороту. Весь каталог отображается сразу по кнопке «Добавить инструменты» на Watchlist, стартовые цены загружаются пакетным запросом. По умолчанию в избранном (Watchlist) только SBER, GAZP, LKOH и YDEX — остальные из каталога пользователь добавляет вручную звёздочкой по мере необходимости; выбор и удаления сохраняются в браузере, поиск и фильтр класса актива работают по всему каталогу. Если сервер ранее был ограничен четырьмя тикерами, очистить `T_INVEST_INSTRUMENTS` в его `.env` и перезапустить backend. Проверка реального каталога: `python backend/check_universe.py`.

Все адаптеры (`backend/tinvest.py` для котировок, `backend/live.py` для чтения счёта, `backend/live_orders.py` для реальных заявок) используют только явно разрешённые методы своего собственного allowlist и проверяют TLS с отдельным CA для T-Invest. `tinvest.py` и `live.py` физически не способны вызвать OrdersService — этого метода просто нет в их allowlist. Единственное место в кодовой базе, где вообще есть вызовы OrdersService, — `live_orders.py`, и там заявка уходит брокеру только из `approve_proposal()`, вызываемой исключительно по явному действию администратора. Сертификат: [официальная инструкция T-Bank](https://developer.tbank.ru/invest/intro/developer/network), источник PEM — `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`. Системное хранилище доверия не меняется.

Часовые SMA50, ATR14, ADX14, RSI14 и 20-барный диапазон рассчитываются на завершённых свечах; нужно минимум 60 завершённых часовых свечей — брокер отдаёт максимум 7 календарных дней за один запрос `CANDLE_INTERVAL_HOUR`, а это обычно только ~5 торговых дней (~40 свечей при сессии ~8,8 ч), поэтому история запрашивается тремя последовательными 7-дневными окнами (21 календарный день, ~14-15 торговых дней) и склеивается — иначе индикаторы почти никогда не набирали бы 60 свечей и вход был бы вечно недоступен. SIGNAL в журнале — кандидат, **не ордер**. Для исполнения не подключены портфель, календарь событий и полная политика риска реального счёта. Облигационные входы запрещены, пока отсутствуют проверенные YTM/дюрация/рейтинг/календарь. В выходные и при закрытой сессии входы запрещены.

Три встроенных Live-плагина (Grid/Trend/MeanReversion в `tinvest.py`) намеренно настроены мягче своих дефолтов из конструктора, чтобы предложения появлялись с разумной частотой, а не только на самых редких, идеальных условиях: Grid принимает вход ближе к средней и дальше от неё вниз (шаг 0.3% вместо 1%, до 15 уровней вместо 5), Trend срабатывает в пределах 1% от уровня пробоя вместо требования полностью его пройти (`Trend.breakout_margin_pct`, по умолчанию 0 — старое строгое поведение), MeanReversion принимает более мелкую просадку (1×ATR вместо 2) и менее экстремальную перепроданность по RSI (40 вместо 30). Это общие параметры для всех пользователей Live, а не персональная настройка — режимные и сессионные ограничения (FLAT/UPTREND/DOWNTREND, открытая сессия, ликвидный стакан) действуют без изменений.

## Live

Терминал многопользовательский: один общий токен в `.env`/настройках нужен только для котировок (`tinvest.py`, `InstrumentsService`/`MarketDataService`), а для реальной торговли **каждый пользователь вводит собственный токен T-Invest в браузере**. Сервер этот торговый токен нигде не хранит и не логирует: он передаётся заголовком `X-Live-Token` только на время конкретного запроса (посмотреть счёт, подтвердить или отменить заявку) и живёт только в `localStorage` того браузера, где его ввели.

**Счёт (чтение).** Диалог Live на шаге 2 просит собственный токен и показывает по нему счёт: `GET /api/live/account` с заголовком `X-Live-Token` вызывает `UsersService.GetAccounts`, `OperationsService.GetPortfolio` и (только чтобы подписать позиции тикером/названием) `InstrumentsService.GetInstrumentBy` — нужен токен с доступом к счёту, это отдельная опция при выпуске токена, не совпадает с правами на котировки. Тот же токен и тот же счёт доступны прямо на странице «Портфель»: кнопка «Live» в шапке показывает реальные позиции (акции и облигации), баланс и свободные деньги — используется тот же `localStorage`-токен, что и в диалоге Live, так что вводить его дважды не нужно. Там же, на «Портфель», при выбранном Live отдельной панелью показаны и «Предложения на подтверждение» — те же, что в диалоге Live, с теми же кнопками «Отправить»/«Скрыть» — так что не обязательно открывать диалог заново, чтобы подтвердить заявку. Каждая попытка размещения заявки пишется в общий audit-журнал (`GET /api/live/audit`) — без токенов, только исход.

**Реальные заявки, только с ручным подтверждением.** Пока приём предложений не включён администратором (`POST /api/live/enabled`, требует `ADMIN_PASSWORD` — это разовый общесистемный выключатель, а не право торговать), сигналы стратегий из `tinvest.py` остаются просто записями в журнале, как раньше. После включения тот же сигнал (реальный, посчитанный по реальным котировкам и индикаторам) дополнительно создаёт **общее** предложение в локальном хранилище (`backend/live_orders.py`, SQLite) — заявка при этом **не уходит брокеру**. Предложение видят все пользователи; каждый решает сам, отправлять ли его на свой счёт: в диалоге Live нажимает «Отправить» (`POST /api/live/orders/{id}/approve` с заголовком `X-Live-Token`), и заявка со своим `orderId` уходит именно на его счёт под его токеном. Один и тот же пользователь не может отправить одно предложение дважды на один счёт; разные пользователи могут независимо отправить его каждый на свой счёт — это не общая очередь на одного, а витрина кандидатов. «Скрыть» ничего не меняет на сервере — это чисто локальный список отклонённых id в `localStorage`, ведь скрыть предложение для себя не значит убрать его у остальных. Предложение протухает через 3 минуты (цена сигнала могла уйти). Kill-switch (`POST /api/live/kill` с `X-Live-Token`) отменяет только заявки, отправленные этим приложением с этого токена на этот счёт — чужие заявки он не видит и не трогает; открытые позиции он не закрывает — это было бы уже автономной сделкой. `POST /api/live/reconcile` с тем же токеном сверяет локально «отправленные» заявки этого счёта с `OrdersService.GetOrders` брокера.

Полностью автономная (без подтверждения) отправка заявок сознательно не реализована.

Общий токен для котировок, ID счёта для их проверки и лимит инструментов можно менять из интерфейса («Настройки T-Invest» в сайдбаре) без пересборки контейнера — форма и общий выключатель `/api/live/enabled` защищены паролем `ADMIN_PASSWORD` из `.env`; если переменная не задана, форма отключена. Смена токена «горячо» пересоздаёт наблюдателя котировок. У администратора нет доступа к чужим торговым токенам, счетам или их заявкам — только к общему журналу исходов без деталей счёта.

## Состав

- `schemas/strategy.schema.json`: JSON Schema 2020-12 для всех восьми классов, включая Event и RiskOff как надстройки.
- `schemas/risk-policy.schema.json`: общая обязательная политика риска.
- `docs/design.md`: матрица режимов, архитектура, UI, дизайн-токены, Live-протокол, особенности облигаций.
- `backend/engine.py`: Decimal-расчёты, RiskEngine, интерфейс Strategy, четыре базовых плагина, paper-брокер и mock ticks.
- `backend/test_engine.py`: тесты риск-инвариантов и облигационного P/L.
- `backend/app.py`: FastAPI с backend-owned такт-циклом и read-only монитором.

## Запуск

Python 3.11+; команды из корня репозитория:

```powershell
python -m unittest discover -s backend -v
python backend/engine.py
python -m pip install -r backend/requirements.txt
python -m uvicorn app:app --app-dir backend --host 127.0.0.1 --port 8000 --workers 1
```

При установленном `uv`, если Python отсутствует в PATH:

```powershell
uv run --no-project python -m unittest discover -s backend -v
uv run --no-project --with-requirements backend/requirements.txt python -m uvicorn app:app --app-dir backend --host 127.0.0.1 --port 8000 --workers 1
```

API: `GET /api/paper/snapshot`, `GET /api/paper/journal`, Swagger `/docs`.
T-Invest: `GET /api/t-invest/snapshot`, `GET /api/t-invest/journal`. Состояние службы: `GET /api/health`.
`GET /api/live/enabled` сообщает, включён ли приём предложений; торговые эндпойнты `/api/live/*` требуют собственный токен пользователя в заголовке `X-Live-Token`.

Проверка схем и API:

```powershell
uv run --no-project --with-requirements backend/requirements.txt python backend/check_contracts.py
uv run --no-project --with-requirements backend/requirements.txt python -m unittest discover -s backend -v
cd frontend
npm run build
npm run test:e2e
```

Backend-тесты покрывают риск-инварианты, облигационный P/L, классификатор, неполные свечи, ошибки авторизации, 429/backoff, пустые ответы и старение котировок. Контрактные тесты никогда не используют реальный токен. Playwright проверяет экраны, конструкторы, сохранение, мобильную компоновку, Live-блокировку и потерю API. На Windows используется Edge; в Linux предварительно выполнить `npx playwright install --with-deps chromium`.

## Границы реализации

Интерфейс реализован; торговое ядро остаётся paper reference. Полные параметры всех стратегий представлены в схемах; четыре Python-плагина демонстрируют базовые сигналы. Breakout и Momentum не исполняются этим примером. Календарный запрет и Risk-off исполняются в RiskEngine.

Paper тикает реальными котировками и часовыми индикаторами того же T-Invest Observer, что и Live-сигналы (`Observer.build_tick`, `backend/app.py`'s `loop()`) — не синтетическим циклом цен. Бумага не тикает вовсе, пока по ней нет свежей котировки, двухстороннего стакана и 60 завершённых часовых свечей; до этого момента её P/L и режим просто не меняются, а не показывают выдуманное движение. PaperBroker исполняет заявку целиком при пересечении лимита, немедленно подтверждает отмену и не моделирует очередь, частичные сделки, биржевые ценовые коридоры, задержку или маржинальное обеспечение. Grid исполняет один уровень без дозаполнения позиции; пирамидинг отключён. Конструкторская схема является контрактом полной системы, а не обещанием поддержки всех параметров paper-движком.

Состояние paper хранится в памяти; перезапуск сбрасывает портфель. Live должен сохранять дневной стоп, резервы, ownership и журнал транзакционно и восстанавливаться через сверку с брокером; архитектура описана в проекте. Купон и амортизация учитываются функцией total-return P/L; paper-цикл не имитирует календарь выплат. Недельная просадка в paper отсчитывается от переданного `week_peak`; недельный календарный rollover не имитируется.

Live умеет выставлять реальные заявки, но только по одной, вручную, после явного включения администратором и подтверждения каждого конкретного предложения самим пользователем его собственным токеном — полностью автономного исполнения нет и оно не планируется без отдельного пересмотра рисков. Предложения создают те же три плагина (Grid/Trend/MeanReversion), что и в paper-режиме, с их дефолтными настройками — то есть каждое предложение всегда на 1 лот; `RiskEngine` из paper-движка их не проверяет и никаких лимитов на сумму/число одобренных заявок нет — единственный риск-контроль сейчас это сам пользователь, читающий предложение перед нажатием «Отправить» на своём счёте. Хранилище предложений — SQLite, не полноценная транзакционная база; сверка с брокером (`GetOrders`) — по запросу пользователя (`/api/live/reconcile`), best-effort и не восстанавливает частично исполненные заявки; автоматической сверки при старте контейнера больше нет, так как сервер не хранит ничьих торговых токенов между запусками. Kill-switch каждого пользователя отменяет только его собственные висящие заявки, но не закрывает уже открытые позиции.

Не является индивидуальной инвестиционной рекомендацией. Торговля связана с риском потери капитала.
